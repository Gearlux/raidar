# Raidar Mandates

- **Two-Track Trainer Surface:** Raidar exposes detection models through two parallel paths. (a) The **specialised trainer** — `LightningDetectionTrainer` (in `lightning_trainer.py`) — overrides step functions and talks to torchvision-native detection models and raw `torchmetrics` metrics (`MeanAveragePrecision`, ...) directly. No adapter layer between trainer and loss/metric. (b) The **marainer-generic path** uses `marainer.trainer.LightningTrainer` unchanged, plus the adapters in `raidar.detection` (`DetectionBatchInput`, `DetectionStepOutput`, `TorchvisionDetectionLoss`, `DetectionMetricAdapter`, `DetectionConfusionMatrix`). Both paths must remain functional. The framework-trainer file naming reserves room for future siblings (`tensorflow_trainer.py`, `fastai_trainer.py`, ...). The ultralytics-backed specialised trainer (`UltralyticsTrainer`) lives in the sibling [raidar-ultralytics](https://github.com/Gearlux/raidar-ultralytics) package — that's where `import ultralytics` belongs.
- **Native is the Default, Marainer-Generic is the Wrapper:** A new detection model ships as `<name>.py` exposing the **torchvision-native API**: `forward(images, targets) → Dict[str, Tensor]` (loss dict) in train mode; `forward(images) → List[Dict[str, Tensor]]` (per-image `{boxes, scores, labels}`) in eval mode. If the model also needs to plug into the marainer-generic trainer flow, ship a sibling `<name>_marainer.py` that wraps the native model into `DetectionStepOutput`. Faster R-CNN is the exception: `faster_rcnn.py` is the marainer-generic adapter, and the specialised trainer consumes a raw `torchvision.models.detection.fasterrcnn_*` directly with no raidar wrapper.
- **Marainer-Path Step Output:** Detection models exposed through `*_marainer.py` (or `faster_rcnn.py`) MUST return the `{losses, predictions}` dict described by `DetectionStepOutput`. The loss adapter sums `losses`; the metric adapter unwraps `predictions`. Don't invent per-detector contracts.
- **Per-Image Prediction Schema:** Use `marainer.outputs.DetectionOutput` / `DetectionPredictions` as the task-agnostic prediction record across both paths. Re-export from `raidar.detection`; never define a parallel schema.
- **Collate Discipline:** Variable-length per-image targets MUST be carried through `detection_collate_fn` as lists — never padded to a fixed shape, never silently dropped. The specialised trainer's step methods unwrap `DetectionBatchInput` into `(images, targets)` before handing to the native model.
- **No `import ultralytics` in Raidar (the line is the *import*, not the format):** Any code that actually imports `ultralytics` — ultralytics-backed detectors, the native ultralytics trainer/evaluator — belongs in the `raidar-ultralytics` sibling package, never here; raidar MUST stay installable without `ultralytics`. Code that merely *targets* the ultralytics/YOLO **format** but does NOT import `ultralytics` MAY live in raidar — e.g. `raidar.UltralyticsSink` (the DataFlux `DataSink` that writes the on-disk YOLO dataset layout — `data.yaml` / `images/<split>` / `labels/<split>` / COCO sidecar — using only numpy/PIL/yaml; `marainer convert` streams a detection Flux into it via `DatasetProcessor`, one split per run, merging `data.yaml` across runs). It is the on-disk counterpart of the in-memory `raidar_ultralytics.flux_yolo_dataset.FluxYOLODataset` (which DOES import ultralytics-adjacent machinery and recomputes per epoch).
- **Discovery Tags (`task`/`role`):** Raidar's detection `@configurable` classes are tagged `@configurable(task="detection", role=…)` — `FasterRCNNModel` / `RFDETRModel` → `role="model"`, `TorchvisionDetectionLoss` → `role="loss"`, `LightningDetectionTrainer` → `role="trainer"`, the evaluator → `role="evaluator"` (each derives the matching `category`, e.g. `detection_model` / `detection_loss`, so navigaitor's `list_configurable_classes(category=…)` / `list_classes(task=…, role=…)` and the form-spec enumerate them). Preserve the tags when adding/renaming — `tests/test_categories.py` pins them; a dropped tag silently empties the corresponding detection picker and drops the trainer out of navigaitor's `role="trainer"` scan (`TASK_REGISTRY` + `generate_task_config`).
- **Explicit `num_classes` (derivation removed):** `LightningDetectionTrainer` takes `num_classes: Optional[int] = None` (`self.num_classes = int(num_classes) if num_classes is not None else None`) carried only for parity / the `class_names` sidecar — the mAP metric (`MeanAveragePrecision`) is class-count-agnostic, so its `LazyClass(MeanAveragePrecision)` flows plainly through the base. **Set `num_classes` explicitly on the detection model's config**; the generic `marainer.dimensions` derivation was removed.
