# Raidar Mandates

- **Two-Track Trainer Surface:** Raidar exposes detection models through two parallel paths. (a) The **specialised trainers** — `LightningDetectionTrainer` (in `lightning_trainer.py`) and `UltralyticsTrainer` (in `ultralytics_trainer.py`) — override step functions and talk to torchvision-native detection models and raw `torchmetrics` metrics (`MeanAveragePrecision`, ...) directly. No adapter layer between trainer and loss/metric. (b) The **marainer-generic path** uses `marainer.trainer.LightningTrainer` unchanged, plus the adapters in `raidar.detection` (`DetectionBatchInput`, `DetectionStepOutput`, `TorchvisionDetectionLoss`, `DetectionMetricAdapter`, `DetectionConfusionMatrix`). Both paths must remain functional. The framework-trainer file naming reserves room for future siblings (`tensorflow_trainer.py`, `fastai_trainer.py`, ...).
- **Native is the Default, Marainer-Generic is the Wrapper:** A new detection model ships as `<name>.py` exposing the **torchvision-native API**: `forward(images, targets) → Dict[str, Tensor]` (loss dict) in train mode; `forward(images) → List[Dict[str, Tensor]]` (per-image `{boxes, scores, labels}`) in eval mode. If the model also needs to plug into the marainer-generic trainer flow, ship a sibling `<name>_marainer.py` that wraps the native model into `DetectionStepOutput`. Faster R-CNN is the exception: `faster_rcnn.py` is the marainer-generic adapter, and the specialised trainer consumes a raw `torchvision.models.detection.fasterrcnn_*` directly with no raidar wrapper.
- **Marainer-Path Step Output:** Detection models exposed through `*_marainer.py` (or `faster_rcnn.py`) MUST return the `{losses, predictions}` dict described by `DetectionStepOutput`. The loss adapter sums `losses`; the metric adapter unwraps `predictions`. Don't invent per-detector contracts.
- **Per-Image Prediction Schema:** Use `marainer.outputs.DetectionOutput` / `DetectionPredictions` as the task-agnostic prediction record across both paths. Re-export from `raidar.detection`; never define a parallel schema.
- **Collate Discipline:** Variable-length per-image targets MUST be carried through `detection_collate_fn` as lists — never padded to a fixed shape, never silently dropped. The specialised trainer's step methods unwrap `DetectionBatchInput` into `(images, targets)` before handing to the native model.
- **Ultralytics Escape Hatch:** Native Ultralytics training (mosaic + albumentations + Ultralytics `LOGGER`) lives behind `UltralyticsTrainer` / `UltralyticsEvaluator` in `ultralytics_trainer.py`, registered as `ultralytics-train` / `ultralytics-evaluate` marainer verbs via the `marainer.commands` entry point. The trainer accepts the raw underlying ultralytics `DetectionModel` (built internally from `variant` or supplied via the `model` parameter) — no raidar model wrapper is required. Flux mode swaps the on-disk `YOLODataset` for `FluxYOLODataset` — no on-disk `data.yaml` required — and accepts the workspace's `train_set` / `val_set` / `num_classes` / `class_names` convention as a more ergonomic alternative to the legacy `data: {...}` dict form. The `augment: bool | None` knob controls whether ultralytics' own mosaic / albumentations pipeline fires; set `augment: false` to disable it and have dataflux Flux ops own augmentation upstream. When `augment: true`, the `augmentation: {mosaic, mixup, hsv_h, fliplr, ...}` dict surfaces ultralytics' augmentation hyperparams directly from YAML — key names match ultralytics' own config vocabulary verbatim. An optional `val_metric: torchmetrics.Metric | MetricCollection` runs a torchmetrics pass over `val_set` after the ultralytics built-in loop completes; results ride alongside the native `DetMetrics` sidecar.
- **Manifest Discoverability:** New models / losses / metrics belong under `manifests/` so navigaitor's scanner can auto-expose them; match existing `<name>.yaml` conventions. When a model ships both a native and a marainer-generic class, register both manifests.
