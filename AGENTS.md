# Raidar Mandates

- **Single Native Detection Path (no adapter layer):** Detection runs **exclusively** through the specialised, torchvision-native surface — `LightningDetectionTrainer` (`lightning_trainer.py`) and `LightningDetectionEvaluator` (`evaluator.py`) **override** the step functions and talk to torchvision-native detection models and raw `torchmetrics` metrics (`MeanAveragePrecision`, `raidar.detection.DetectionConfusionMatrix`, ...) directly. There is **no** marainer-generic adapter path: the old `DetectionStepOutput` / `TorchvisionDetectionLoss` / `DetectionMetricAdapter` indirection and the `*_marainer.py` wrapper models (`faster_rcnn.py`, `rfdetr_marainer.py`) were **removed**. Do NOT reintroduce a `DetectionStepOutput`-style `{losses, predictions}` contract, a loss/metric adapter, or a base-`LightningTrainer` detection path. **Framework-native trainers that wrap an UPSTREAM library's OWN train/eval loop are also permitted — one module per framework** (`rfdetr_trainer.py` → `RFDETRTrainer`/`RFDETREvaluator`, driving RF-DETR's own `RFDETRModelModule`/`RFDETRDataModule`/`build_trainer`; the framework-trainer file naming reserves room for `tensorflow_trainer.py`, ...). Such a trainer drives the upstream loop directly and adds ONLY a `Dataset`/`DataModule` bridge (native plumbing — `raidar.flux_rfdetr_dataset`, the in-memory counterpart of `FluxYOLODataset`) — it MUST NOT reintroduce a marainer-generic adapter; the upstream library owns its loss/metric/loop. **In-core admission is licensed by permissive licensing:** RF-DETR is Apache-2.0, so `RFDETRTrainer` lives in core raidar; AGPL frameworks stay in a sibling — the ultralytics-backed `UltralyticsTrainer` lives in [raidar-ultralytics](https://github.com/Gearlux/raidar-ultralytics), where `import ultralytics` belongs.
- **Native RF-DETR trainer (`rfdetr_trainer.py`) — tagged for navigaitor multi-trainer discovery:** `RFDETRTrainer` / `RFDETREvaluator` are `@configurable(task="detection", role="trainer"/"evaluator")` — so `(detection, trainer)` and `(detection, evaluator)` now resolve to **TWO** classes each (the Lightning pair + the RF-DETR pair), and navigaitor navigates multiple trainers per task (see navigaitor's "A Task May Have MULTIPLE Trainers" mandate). Both support **disk mode** (`data=` COCO/YOLO/Roboflow dir → RF-DETR's native `.train()`) AND **in-memory Flux mode** (`train_set`/`val_set` + `num_classes` + `class_names`, fed via `FluxRFDETRDataModule` — NO disk materialization; the Flux dataset reuses RF-DETR's `ConvertCoco` + `make_coco_transforms` for byte-faithful items, and caches labels via `dataflux.iter_targets` target-only projection). Flux mode reimplements `RFDETR.train()`'s tail (build `RFDETRModelModule` + datamodule + `build_trainer` + `fit`) — keep it to the PUBLIC building blocks (drift risk vs `rfdetr/detr.py`); the gated `tests/test_rfdetr_trainer.py::test_flux_train_smoke` catches breakage on a dependency bump (it trains on the best available accelerator via the module-local `_best_available_device()` helper — CUDA→MPS→CPU — so it is ~25 s on an MPS/GPU host vs ~8 min pinned to CPU; CPU-only CI runners still pay the full cost). **Labels are 0-indexed `0..K-1`** (RF-DETR reserves background at index `K` — the OPPOSITE of torchvision's background-at-0; examples use `CocoToTorchVisionDetectionOp(label_offset=0)`, NOT `+1`). Hard deps: `rfdetr[train,loggers]` (PTL + RF-DETR's training stack) + `faster-coco-eval` (the torchmetrics backend RF-DETR's `COCOEvalCallback` requires for mAP — NOT pulled by `rfdetr[train]`). CLI: `raidar-rfdetr train`/`evaluate` (`rfdetr_cli.py`) + `marainer rfdetr-train`/`rfdetr-evaluate` (`rfdetr_plugin.py`). The MLflow run-name knob is `run_name` (NOT `run` — that would shadow the `run()` method). Pins: `tests/test_rfdetr_trainer.py`, `tests/test_flux_rfdetr_dataset.py`, `tests/test_rfdetr_plugin.py`, `tests/test_categories.py::test_detection_is_a_multi_trainer_task`.
- **Native Model API (the shape torchvision detectors already speak):** A detection model ships as `<name>.py` exposing `forward(images, targets) → Dict[str, Tensor]` (loss dict) in train mode and `forward(images) → List[Dict[str, Tensor]]` (per-image `{boxes, scores, labels}`) in eval mode. The trainer sums the loss dict for the optimisation scalar and feeds the prediction list straight to the metric. Torchvision Faster R-CNN conforms **raw** — pass `torchvision.models.detection.fasterrcnn_*` directly, no raidar wrapper. RF-DETR ships a native module (`raidar.rfdetr.RFDETRModel`); the ultralytics-family natives live in `raidar-ultralytics`.
- **Hugging Face transformers detectors (`hf_detection.py`) — native model wrappers, NO bespoke trainer:** `raidar.hf_detection` wraps `transformers` object detectors into the Native Model API above — `HFDetectionModel` (generic, any HF object-detection `model_id`) + the two Apache-2.0 presets `DFINEModel` (D-FINE) and `RTDETRv2Model` (RT-DETRv2). Because they are Apache-2.0 they live in core raidar (the "in-core admission is licensed by permissive licensing" rule — like RF-DETR, unlike AGPL ultralytics). **They run through the EXISTING `LightningDetectionTrainer`/`LightningDetectionEvaluator` (`raidar train`/`evaluate`), NOT a framework-native trainer.** This is the deliberate CONTRAST with `rfdetr_trainer.py`: RF-DETR has its *own* PTL training loop worth driving, so it earns a framework-native trainer; an HF detector instead computes its Hungarian-matched DETR loss INSIDE `forward(labels=…)` and decodes predictions via its own image processor — there is no separate upstream loop to wrap, so adding an `hf_trainer.py`/CLI/plugin would only DUPLICATE the generic Lightning path and violate the Single Native Detection Path + smallest-change mandates. Do NOT add one. **Footguns / invariants** (all empirically grounded against `transformers` 5.x — see `tests/test_hf_detection.py`): (1) **labels are 0-indexed `0..K-1`** with NO background slot — wire `CocoToTorchVisionDetectionOp(label_offset=0)`, the SAME as RF-DETR and the OPPOSITE of torchvision's `+1`; (2) **input must be `[0,1]`, NOT ImageNet-normalised** — the RT-DETR/D-FINE processors run `do_normalize=False`, so feed `ToTensorOp(normalize=True)` output straight through and NEVER add a `StandardizeOp` (double-normalising silently wrecks accuracy); (3) **the wrapper resizes images to a square `image_size` (default 640) INTERNALLY and decodes predictions back into each image's original pixel space** via per-image `target_sizes` — so the SAME op chain as `train_fasterrcnn_cppe5_hf.yaml` drops in with no detection-aware resize op (a deliberate divergence from `RFDETRModel`/`YOLO26Model`, which instead REQUIRE pre-resized square images and raise); (4) **custom class counts re-init the head** — `from_pretrained(model_id, num_labels=K, ignore_mismatched_sizes=True)` keeps backbone/encoder/decoder pretrained, re-inits only the class head when `K != 80`. Presets expose a closed-`Literal` `variant` mapped to checkpoint ids via `_DFINE_CHECKPOINTS`/`_RTDETRV2_CHECKPOINTS` (keyed off the Literal via `get_args` — one source of truth), and accept `num_classes` so a `!lazy:` model gets the dataset-derived count injected by the trainer's `initialize()`. Hard deps: `transformers>=4.49` (D-FINE landed v4.48, RT-DETRv2 v4.49) + `timm` (backbones) + `scipy` (the DETR-family Hungarian matcher). Tagged `@configurable(task="detection", role="model")` → `detection_model` (navigaitor/FluxStudio pickers). **Why not Megvii YOLOX (the original ask):** its upstream is frozen (PyPI `yolox` 0.3.0, py≤3.11/torch 1.x) and won't install on this workspace's py3.12/torch2.11 — D-FINE/RT-DETRv2 are the maintained, permissively-licensed alternatives chosen instead (a true CNN-YOLO would need vendoring; tracked in root `TASKS.md`). Pins: `tests/test_hf_detection.py`, `tests/test_categories.py::test_hf_detection_models_task_role_tagged`.
- **Per-Image Prediction Schema:** Use `marainer.outputs.DetectionOutput` / `DetectionPredictions` as the task-agnostic prediction record. Re-export from `raidar.detection`; never define a parallel schema.
- **Collate Discipline:** Variable-length per-image targets MUST be carried through `detection_collate_fn` as lists — never padded to a fixed shape, never silently dropped. The trainer/evaluator step methods unwrap `DetectionBatchInput` into `(images, targets)` before handing to the native model. `DetectionBatchInput` + `detection_collate_fn` are native batch plumbing (not adapters) and stay in `raidar.detection`.
- **No `import ultralytics` in Raidar (the line is the *import*, not the format):** Any code that actually imports `ultralytics` — ultralytics-backed detectors, the native ultralytics trainer/evaluator — belongs in the `raidar-ultralytics` sibling package, never here; raidar MUST stay installable without `ultralytics`. Code that merely *targets* the ultralytics/YOLO **format** but does NOT import `ultralytics` MAY live in raidar — e.g. `raidar.YoloSink` (the DataFlux `DataSink` that writes the on-disk YOLO dataset layout — `data.yaml` / `images/<split>` / `labels/<split>` / COCO sidecar — using only numpy/PIL/yaml; `marainer convert` streams a detection Flux into it via `DatasetProcessor`, one split per run, merging `data.yaml` across runs). `YoloSink` carries `@configurable(category="sink")` so FluxStudio ALSO surfaces it as a `DatasetProcessor` sink node (`DATAFLUX_OBJECT:sink`) — the canvas convert pipeline mirrors the YAML one. It is the on-disk counterpart of the in-memory `raidar_ultralytics.flux_yolo_dataset.FluxYOLODataset` (which DOES import ultralytics-adjacent machinery and recomputes per epoch). **`source_metadata` is best-effort JSON via `_jsonable_metadata`, which MUST NEVER raise:** `Sample.metadata` reaching the sink can carry values `json.dumps` rejects — **complex** IQ samples and FluxStudio's internal `__taidal_stash_*` snapshots (a stashed complex signal from a DAG→sequential fan-out) — so `_jsonable_metadata` stringifies a `complex` scalar, SUMMARISES a large array (> `_MAX_META_ARRAY_ELEMS`) as `<array shape=… dtype=…>` (a 1.2M-element IQ stash must not bloat every per-image label JSON), and RECURSES into `.tolist()` output so nested complex/NumPy scalars are sanitised too (the bug it fixed: returning `.tolist()` un-recursed left a list of Python `complex` that still crashed `json.dumps`). Don't "simplify" it back to a naive `tolist()`. Pins: `tests/test_yolo_sink.py::test_jsonable_metadata_sanitizes_complex_and_large_arrays` / `::test_jsonable_metadata_small_complex_array_becomes_strings` / `::test_metadata_jsonl_survives_complex_stash_array`.
- **Discovery Tags (`task`/`role`):** Raidar's detection `@configurable` classes are tagged `@configurable(task="detection", role=…)` — `RFDETRModel` → `role="model"` (derives `category="detection_model"`), `LightningDetectionTrainer` → `role="trainer"`, `LightningDetectionEvaluator` → `role="evaluator"` — so navigaitor's `list_configurable_classes(category=…)` / `list_classes(task=…, role=…)` and the form-spec enumerate them. There is intentionally **no** `role="loss"` detection class: the native trainer computes loss inside the model's `forward` (`loss_fn` is `None`), so navigaitor's `generate_task_config` finds no loss slot. The native metric `DetectionConfusionMatrix` is a plain `torchmetrics.Metric` (untagged, wired via `!class:` in a `MetricCollection`, like `MeanAveragePrecision`). Preserve the tags when adding/renaming — `tests/test_categories.py` pins them; a dropped tag silently empties the detection picker and drops the trainer/evaluator out of navigaitor's scan (`TASK_REGISTRY` + `generate_task_config`).
- **Torchvision Detection Builders Are `register`-ed as `detection_model` (`raidar/configurables.py`):** Torchvision ships its detectors as builder FUNCTIONS, not classes. `raidar.configurables` `register`s the full family — `fasterrcnn_resnet50_fpn` / `_v2` / `fasterrcnn_mobilenet_v3_large_fpn` / `_320_fpn` / `retinanet_resnet50_fpn` / `_v2` / `fcos_resnet50_fpn` / `ssd300_vgg16` / `ssdlite320_mobilenet_v3_large` — with `register(fn, task="detection", role="model", group="detection", lazy=True)`. So each raw builder is offered in navigaitor's `detection_model` picker BESIDE `RFDETRModel`, and FluxStudio generates a `DATAFLUX_OBJECT:model` object node for it (widgets introspected from the builder's own signature) that wires straight into the trainer's `model` slot — no wrapper class, no Retag. This works because confluid's `to_pydantic`/`flow`/`resolve_class` are callable-aware (confluid AGENTS "A Target May Be ANY Callable"); `lazy=True` keeps the constructed value deferred so the trainer's `initialize()` injects the dataset-derived `num_classes`. The builders are STILL also usable raw by dotted `!lazy:` path (the `register` adds discoverability, it does not replace the dotted-path form). **Mask R-CNN / Keypoint R-CNN are deliberately excluded** — they need instance-mask / keypoint targets, not the `{boxes, labels}` shape `detection_collate_fn` produces. A second `confluid.configurables` entry point (`raidar-configurables = "raidar.configurables"`) + `__all__` exposes them to FluxStudio's `__all__`-gated discovery pass. Pins: `tests/test_categories.py::test_torchvision_builders_registered_as_detection_models` / `::test_torchvision_builder_generates_config_schema`.
- **`num_classes` Resolved in `initialize()` + Injected into a `!lazy:` Model (mirrors sonair):** `LightningDetectionTrainer` resolves `num_classes` at run time in an explicit `initialize()` (called at the top of `run()`, BEFORE `super().run()`) and flows the model with it — so a `!lazy:` model can OMIT `num_classes` and have it derived from the data, exactly like `sonair.LightningClassificationTrainer`. Resolution order (`_resolve_num_classes`): a **concrete (non-`Fluid`) model's head is authoritative** (`_model_num_classes` — an explicit `num_classes` attr, e.g. `RFDETRModel`/`YOLO26Model`, or torchvision's `roi_heads.box_predictor.cls_score.out_features`) → explicit trainer arg → a lazy model's pinned `num_classes` kwarg → **derived from the train targets** (`max(label)+1`; the last-resort path, walks the set, logs progress). The count is injected via `flow(self.model, num_classes=…)` **only when the model is still deferred AND its builder accepts `num_classes`** (`_model_accepts_num_classes`); a builder without that param is flowed plainly. This relies on confluid's **callable-target** support — `flow()` passes `num_classes` to a `!lazy:torchvision.models.detection.fasterrcnn_resnet50_fpn` builder *function* (see confluid AGENTS "A Target May Be ANY Callable"). The default mAP metric is class-count-agnostic, so `num_classes` only sizes the model head. For torchvision's background-at-0 convention, dataset 0-indexed categories need a `+1` shift (do it in the target op, e.g. `dataflux.ops.target.CocoToTorchVisionDetectionOp(label_offset=1)`). **Inputs are `Mandatory[...]`** (`model` / `train_set`) and the trainer exposes the `trained_model` `@output`; ergonomic flat-config knobs (`max_epochs` / `batch_size` / `num_workers` / `logger`) broadcast in. Reference flat HF example: `examples/train_fasterrcnn_cppe5_hf.yaml`. Pins: `tests/test_lightning_trainer.py` (the `initialize()` / `_model_num_classes` / `trained_model` tests). **The evaluator (`LightningDetectionEvaluator`) is the eval-side mirror of `sonair.LightningClassificationEvaluator` — model-driven, with NO `num_classes` ctor knob.** Its `initialize()` (called at the top of `run()`, BEFORE `super().run()`) **flows the model FIRST** and reads `num_classes` straight off the live trained model (`_model_num_classes` — the model loaded its own checkpoint, so its head is the single source of truth, NOT the eval dataset which may be a subset); the read is **best-effort** (the default MAP metric is class-count-agnostic, so an undeterminable count leaves `self.num_classes` `None` instead of raising — the one deliberate deviation from sonair, whose per-class metrics require it). `initialize()` also normalizes the wired dataset to a `Dataset[Sample]` via marainer's `ensure_sample_dataset`. There is no evaluator `num_classes` constructor argument — passing one raises `TypeError`; the top-level YAML `num_classes` broadcasts into the *model* (e.g. `YOLO26Model`) to size its head, not into the evaluator. Pins: `tests/test_detection_evaluator.py` (the `initialize()` / model-driven `num_classes` / `test_no_num_classes_ctor_arg` tests).
