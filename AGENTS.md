2.285114049911499 / `val/map_50` 0.00020625352105024217, byte-identical under csv AND mlflow
and across reruns:** the first full-fleet MLflow sweep caught the seeded keras cell landing
2.2993 under a live MlflowTracker while csv/direct runs reproduced 2.30023455619812 — both arms
deterministic, so it read as a seed leak. The bisect proved initial weights, row order, the
first batch's bytes and all four RNG streams identical at `model.fit` entry, then python's
global `random` alone diverging inside `on_train_begin` and the tensors entering step 0
differing: Keras's PyDataset adapter permutes BATCH order via the global `random.shuffle`, and
mlflow's telemetry client draws one `random.randint` at run creation — after the seed, before
the first shuffle draw. The fix is matrainer's (`KerasRunnable`'s `model.fit` now passes
`shuffle=False` — the RecordSequence already owns row order with a private seeded RNG,
reshuffled per epoch; matrainer `docs/architecture.md` record 9 amendment 6), so pre-fix keras
digits are NOT bit-comparable across it. The other engines never read ambient RNG for order and
kept their canonicals. Those are BIT-COMPARABLE across a refactor, and three of them are byte-for-byte
what the same engines produced before the collate rework AND before the frame-guard work — which
is what proves both perturbed nothing. `keras` was the one engine that could NOT prove that: it
alone had no `seed` knob, and three runs of the identical config gave 2.27 / 2.18 / 2.12, so the
engine you would ask to confirm a refactor was silently the one that could not. `KerasFcos` gained
the knob its four siblings already carried (2026-08-06, `keras.utils.set_random_seed` before the
build) and has since produced 2.30023455619812 on three consecutive runs. All five implementations
are seeded, derived-pinned by `tests/test_fcos_spec.py::test_every_implementation_is_SEEDED` so the
next one cannot join without it, with `test_the_keras_seed_actually_reproduces_the_weights`
asserting the knob BINDS (same seed → identical weights, different seed → different) rather than
merely existing. **Re-verified end to end 2026-08-06** after the frame-guard work, all five non-spec backends
exiting 0 on the same slice: `torch` train/loss 0.5360 with val/map_50 0.3436, `fastai` 0.5436 /
0.2203, `lightning` test/map_50 0.3632, `huggingface` 3m43s, `rfdetr` 2m36s — the first three
matching their recorded numbers. **`rfdetr` and `huggingface` were the OTHER two unseeded runs, and BOTH
had the SAME defect — the seed applied after the model was built (fixed 2026-08-06):** each
framework does seed itself, but too late to cover the network. `transformers.Trainer` applies
`TrainingArguments.seed` when TRAINING starts, by which time `HuggingFaceDetector` has already
constructed the model and randomly initialized its `num_classes` head; `RFDETRModelModule`'s
`on_fit_start` calls `seed_everything(seed + rank)`, which is after BOTH rfdetr fit paths have
run `_build_rf`. So in each case the data order was seeded and the WEIGHTS were not. The fixes
mirror each other: `HuggingFaceDetector` takes a declared `seed` (default 42 — the transformers
default, so nobody's behaviour changed) applied via `transformers.set_seed` BEFORE the model is
flowed and passed on into the `TrainingArguments` floor so the two cannot disagree; the rfdetr
backend applies `seed_everything(seed, workers=True)` at the top of both fit paths, taking the
value from the `train_config` pass-through (`RF-DETR's TrainConfig.seed` defaults to **None** —
it seeds nothing unless asked, which is why the example config now pins `train_config: {seed: 7}`).
**Both are CONFIRMED fixed, and rfdetr carries one caveat.** huggingface:
two runs land identical (train/loss 40.41484375, val/map_50 0.046988025307655334). rfdetr **on
cpu**: two runs land identical at mAP50:95 **0.355725** — but **on mps it still varies** (0.29446
/ 0.333115), so the residual is Apple's MPS backend, not a seed: pin `device: cpu` on the rfdetr
block for a bit-comparable run and accept mps as fast-but-not-reproducible. **The order of those
experiments is the lesson, and it cost two wrong conclusions:** a cpu-vs-mps comparison run BEFORE
the ordering fix CANNOT isolate the device, because the unseeded model init dominates both arms —
it gave 0.3777 / 0.3453 on cpu and was briefly written up here as "the device is rejected", which
the evidence never supported. Fix the seeding first, THEN vary the device. The pre-fix draws, kept
as the evidence: rfdetr mAP50:95 0.3156 / 0.3819 (the
once-recorded 0.372 sits BETWEEN them), huggingface eval_loss 8.001 / 6.277 with val/map_50
0.0685 / 0.1302 — a 3.4x spread against a recorded 0.038 that was only ever one draw. The upstream fixes this cycle: recordstream's `to_tensor` mode-coercion,
`HuggingFaceSource.__len__` clamp, the `ResizeDetection` coupled image+boxes resize op, and the
`Boxes` annotation widened to admit `[N, 4]` tensors, and **`batch_boxes`** — the collate

- **There Is NO `logger:` Slot — `trackers:` Is The Only Output Wiring, And It Is A CONSTRUCTOR Param (2026-08-04):** the old `logger` knob held `pytorch_lightning.loggers.*` and is DELETED. Stored VERBATIM; `_live_trackers()` normalizes + flows ONCE, writing back (a `Fluid` re-flowed per call would open two MLflow runs for one training run). Every backend also declares `metric_names: Optional[Partial[MetricNames]]`, stored verbatim; the canonical recorded names are `train/loss` (+ `train/loss_step` for the progress bar — Lightning appends `_step`/`_epoch` only when ONE name carries both), `val/loss`-less eval splits (a torchvision model in eval mode returns predictions, not losses) and `<split>/<metric>`.
- **Metrics Are Declared PER SPLIT, The Rule Is matrainer's, And Detection Has NO Train Slot (2026-08-04):** `metrics:` is what every EVAL split measures; `val_metrics:`/`test_metrics:` add to one split, combined by **`matrainer.metric_slots.merge_metric_specs`** (never re-derived inline) and built through `build_metric_collection(...)` with NO `num_classes` flow dim (detection metrics score box overlap, not a fixed-width head), then `.clone(prefix=…)`.
