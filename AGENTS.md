# Raidar Mandates

- **Single Native Detection Path (no adapter layer):** Detection runs **exclusively** through the specialised, torchvision-native surface — `LightningDetectionTrainer` (`lightning_trainer.py`) and `LightningDetectionEvaluator` (`evaluator.py`) **override** the step functions and talk to torchvision-native detection models and raw `torchmetrics` metrics (`MeanAveragePrecision`, `raidar.detection.DetectionConfusionMatrix`, ...) directly. There is **no** marainer-generic adapter path: the old `DetectionStepOutput` / `TorchvisionDetectionLoss` / `DetectionMetricAdapter` indirection and the `*_marainer.py` wrapper models (`faster_rcnn.py`, `rfdetr_marainer.py`) were **removed**. Do NOT reintroduce a `DetectionStepOutput`-style `{losses, predictions}` contract, a loss/metric adapter, or a base-`LightningTrainer` detection path. The framework-trainer file naming reserves room for future siblings (`tensorflow_trainer.py`, ...). The ultralytics-backed specialised trainer (`UltralyticsTrainer`) lives in the sibling [raidar-ultralytics](https://github.com/Gearlux/raidar-ultralytics) package — that's where `import ultralytics` belongs.
- **Native Model API (the shape torchvision detectors already speak):** A detection model ships as `<name>.py` exposing `forward(images, targets) → Dict[str, Tensor]` (loss dict) in train mode and `forward(images) → List[Dict[str, Tensor]]` (per-image `{boxes, scores, labels}`) in eval mode. The trainer sums the loss dict for the optimisation scalar and feeds the prediction list straight to the metric. Torchvision Faster R-CNN conforms **raw** — pass `torchvision.models.detection.fasterrcnn_*` directly, no raidar wrapper. RF-DETR ships a native module (`raidar.rfdetr.RFDETRModel`); the ultralytics-family natives live in `raidar-ultralytics`.
- **Per-Image Prediction Schema:** Use `marainer.outputs.DetectionOutput` / `DetectionPredictions` as the task-agnostic prediction record. Re-export from `raidar.detection`; never define a parallel schema.
- **Collate Discipline:** Variable-length per-image targets MUST be carried through `detection_collate_fn` as lists — never padded to a fixed shape, never silently dropped. The trainer/evaluator step methods unwrap `DetectionBatchInput` into `(images, targets)` before handing to the native model. `DetectionBatchInput` + `detection_collate_fn` are native batch plumbing (not adapters) and stay in `raidar.detection`.
- **No `import ultralytics` in Raidar (the line is the *import*, not the format):** Any code that actually imports `ultralytics` — ultralytics-backed detectors, the native ultralytics trainer/evaluator — belongs in the `raidar-ultralytics` sibling package, never here; raidar MUST stay installable without `ultralytics`. Code that merely *targets* the ultralytics/YOLO **format** but does NOT import `ultralytics` MAY live in raidar — e.g. `raidar.YoloSink` (the DataFlux `DataSink` that writes the on-disk YOLO dataset layout — `data.yaml` / `images/<split>` / `labels/<split>` / COCO sidecar — using only numpy/PIL/yaml; `marainer convert` streams a detection Flux into it via `DatasetProcessor`, one split per run, merging `data.yaml` across runs). It is the on-disk counterpart of the in-memory `raidar_ultralytics.flux_yolo_dataset.FluxYOLODataset` (which DOES import ultralytics-adjacent machinery and recomputes per epoch).
- **Discovery Tags (`task`/`role`):** Raidar's detection `@configurable` classes are tagged `@configurable(task="detection", role=…)` — `RFDETRModel` → `role="model"` (derives `category="detection_model"`), `LightningDetectionTrainer` → `role="trainer"`, `LightningDetectionEvaluator` → `role="evaluator"` — so navigaitor's `list_configurable_classes(category=…)` / `list_classes(task=…, role=…)` and the form-spec enumerate them. There is intentionally **no** `role="loss"` detection class: the native trainer computes loss inside the model's `forward` (`loss_fn` is `None`), so navigaitor's `generate_task_config` finds no loss slot. The native metric `DetectionConfusionMatrix` is a plain `torchmetrics.Metric` (untagged, wired via `!class:` in a `MetricCollection`, like `MeanAveragePrecision`). Preserve the tags when adding/renaming — `tests/test_categories.py` pins them; a dropped tag silently empties the detection picker and drops the trainer/evaluator out of navigaitor's scan (`TASK_REGISTRY` + `generate_task_config`).
- **Torchvision Detection Builders Are `register`-ed as `detection_model` (`raidar/configurables.py`):** Torchvision ships its detectors as builder FUNCTIONS, not classes. `raidar.configurables` `register`s the full family — `fasterrcnn_resnet50_fpn` / `_v2` / `fasterrcnn_mobilenet_v3_large_fpn` / `_320_fpn` / `retinanet_resnet50_fpn` / `_v2` / `fcos_resnet50_fpn` / `ssd300_vgg16` / `ssdlite320_mobilenet_v3_large` — with `register(fn, task="detection", role="model", group="detection", lazy=True)`. So each raw builder is offered in navigaitor's `detection_model` picker BESIDE `RFDETRModel`, and FluxStudio generates a `DATAFLUX_OBJECT:model` object node for it (widgets introspected from the builder's own signature) that wires straight into the trainer's `model` slot — no wrapper class, no Retag. This works because confluid's `to_pydantic`/`flow`/`resolve_class` are callable-aware (confluid AGENTS "A Target May Be ANY Callable"); `lazy=True` keeps the constructed value deferred so the trainer's `initialize()` injects the dataset-derived `num_classes`. The builders are STILL also usable raw by dotted `!lazy:` path (the `register` adds discoverability, it does not replace the dotted-path form). **Mask R-CNN / Keypoint R-CNN are deliberately excluded** — they need instance-mask / keypoint targets, not the `{boxes, labels}` shape `detection_collate_fn` produces. A second `confluid.configurables` entry point (`raidar-configurables = "raidar.configurables"`) + `__all__` exposes them to FluxStudio's `__all__`-gated discovery pass. Pins: `tests/test_categories.py::test_torchvision_builders_registered_as_detection_models` / `::test_torchvision_builder_generates_config_schema`.
- **`num_classes` Resolved in `initialize()` + Injected into a `!lazy:` Model (mirrors sonair):** `LightningDetectionTrainer` resolves `num_classes` at run time in an explicit `initialize()` (called at the top of `run()`, BEFORE `super().run()`) and flows the model with it — so a `!lazy:` model can OMIT `num_classes` and have it derived from the data, exactly like `sonair.LightningClassificationTrainer`. Resolution order (`_resolve_num_classes`): a **concrete (non-`Fluid`) model's head is authoritative** (`_model_num_classes` — an explicit `num_classes` attr, e.g. `RFDETRModel`/`YOLO26Model`, or torchvision's `roi_heads.box_predictor.cls_score.out_features`) → explicit trainer arg → a lazy model's pinned `num_classes` kwarg → **derived from the train targets** (`max(label)+1`; the last-resort path, walks the set, logs progress). The count is injected via `flow(self.model, num_classes=…)` **only when the model is still deferred AND its builder accepts `num_classes`** (`_model_accepts_num_classes`); a builder without that param is flowed plainly. This relies on confluid's **callable-target** support — `flow()` passes `num_classes` to a `!lazy:torchvision.models.detection.fasterrcnn_resnet50_fpn` builder *function* (see confluid AGENTS "A Target May Be ANY Callable"). The default mAP metric is class-count-agnostic, so `num_classes` only sizes the model head. For torchvision's background-at-0 convention, dataset 0-indexed categories need a `+1` shift (do it in the target op, e.g. `dataflux.ops.target.CocoToTorchVisionDetectionOp(label_offset=1)`). **Inputs are `Mandatory[...]`** (`model` / `train_set`) and the trainer exposes the `trained_model` `@output`; ergonomic flat-config knobs (`max_epochs` / `batch_size` / `num_workers` / `logger`) broadcast in. Reference flat HF example: `examples/train_fasterrcnn_cppe5_hf.yaml`. Pins: `tests/test_lightning_trainer.py` (the `initialize()` / `_model_num_classes` / `trained_model` tests).
