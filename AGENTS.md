# Raidar Mandates

- **Adapter, Not Detector:** Raidar wraps `torchvision`, `ultralytics`, and `rfdetr` so their detectors plug into the **unchanged** `marainer.trainer.LightningTrainer` step flow. The base `LightningTrainer.training_step` / `validation_step` MUST remain unchanged — no overridden step functions, no custom Lightning module behaviour. Adapt on either side via `DetectionBatchInput`, `DetectionStepOutput`, `TorchvisionDetectionLoss`, and `DetectionMetricAdapter`. A thin subclass that only sets default `loss_fn` / `collate_fn` / `metrics` / `optimizer` in `__init__` (cf. `LightningDetectionTrainer`) is permitted and is the canonical user-facing surface.
- **Unified Step Output:** Every detector model in raidar MUST return the `{losses, predictions}` dict described by `DetectionStepOutput`. Loss adapters sum `losses`; metric adapters unwrap `predictions`. Don't invent per-detector contracts.
- **Per-Image Prediction Schema:** Use `marainer.outputs.DetectionOutput` / `DetectionPredictions` as the task-agnostic prediction record. Re-export from `raidar.detection`; never define a parallel schema.
- **Collate Discipline:** Variable-length per-image targets MUST be carried through `detection_collate_fn` as lists — never padded to a fixed shape, never silently dropped.
- **Ultralytics Escape Hatch:** Native Ultralytics training (mosaic + albumentations + Ultralytics `LOGGER`) lives behind `UltralyticsTrainer` / `UltralyticsEvaluator`, registered as `ultralytics-train` / `ultralytics-evaluate` marainer verbs via the `marainer.commands` entry point. Flux mode swaps the on-disk `YOLODataset` for `FluxYOLODataset` — no on-disk `data.yaml` required — and accepts the workspace's `train_set` / `val_set` / `num_classes` / `class_names` convention as a more ergonomic alternative to the legacy `data: {...}` dict form. The `augment: bool | None` knob controls whether ultralytics' own mosaic / albumentations pipeline fires; set `augment: false` to disable it and have dataflux Flux ops own augmentation upstream. When `augment: true`, the `augmentation: {mosaic, mixup, hsv_h, fliplr, ...}` dict surfaces ultralytics' augmentation hyperparams directly from YAML — key names match ultralytics' own config vocabulary verbatim.
- **Manifest Discoverability:** New models / losses / metrics belong under `manifests/` so navigaitor's scanner can auto-expose them; match existing `<name>.yaml` conventions.
